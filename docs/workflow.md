# ワークフローと設計判断

これまでの検討で決めた方針の記録です。実装はまだ入っていません。

## 全体の流れ

```text
発散的に画像生成 → generated/99_inbox → 人間が like / dislike / maybe に分類
   → 分類器を作る（scorers/） → 足切り・並べ替え → VLM で再評価
   → 採用 → artifacts/ → GitHub Pages
```

## 概念探索と最終生成

- 発散のための候補（概念探索）は、クラウドの画像生成を使ってもよい。
- ただし、クラウドの生成器で見つけた「方向性」と、最終的に使うモデルが「きれいに描けるか」は別問題。好きだった概念は、最終モデルで再生成して確認する。
- 分類器は生成元ごとに画像の癖が違うため、同じ生成元の画像どうしの順位付けにだけ使う。

## 探索と深掘りを分ける

- **探索（発散）:** 固定の rules と、組み合わせ表（配色 × 形 × 密度 × 対称性 × 線の太さなど）だけを渡す。好みの仕様書は渡さない。渡すと、既知の好みに寄って新しい発見が減る。
- **深掘り（収束）:** 仕様書と、好きな画像の例を渡して絞る。

仕様書（好みの仮説）は `docs/style-spec.md` に置く。必要になった時点で作る。更新は、ラベル付けの 1 ラウンドごとにまとめて行う。

## ディレクトリとラベル

- `generated/` が生成画像の正本。分類器用などに画像を複製しない。
- `like` / `dislike` / `maybe` の意味を固定する。詳細は [generated/README.md](../generated/README.md)。
  - `like`: 手直し・派生の方向が見えて、残したい。「そのまま使える完成品として好き」ではない。
    - `reference`: 既知のパターンとして残す（似た展開が想像できる）
    - `seed`: 未知の方向として残す（ここから複数の派生を見たい）
  - `dislike`: 興味がなく、発展させたい方向も思いつかない
  - `maybe`: 何かありそうだが、手直しの方向が見えない。分類器の学習には使わず、境界の把握や検証に使う
- 発散のラベルは、「具体的な変更案を 1 つ以上思いつき、その結果を見たいか」で決める。回転する道具としての上下・左右の方向性や印刷適性は、最終成形で評価し、発散のラベルには含めない。
- 点数づけ（100 点満点など）はしない。二値＋保留で、数ラウンド分類してから見直す。
- 画像ごとにメタデータ（プロンプト、生成元など）を残す。

## 分類の進め方

- 最初は第一印象で振り分ける。1 枚に長く悩まない。
- 一巡したら、`maybe` と、`like` / `dislike` のうち境界にあるものを見直す。
- 分類器ができたら、人間が見る順番は、自信のある `like`、予測が拮抗するもの、既存データに少ない色・様式のもの、の順にする。

## 分類器

- 分類器は足切り・並べ替え用であり、熱心には育てない。
- 判断の中心は VLM による再評価。ただし VLM の判定も、人間のラベルとの一致率で検証する。
- `scorers/` に、係数・マニフェスト・評価結果の JSON をコミットする。再学習したら上書きし、版の管理は Git の履歴に任せる。
- マニフェストには、参照した画像の ID・ハッシュ・その時点のラベル、埋め込みモデル、学習時点のコミットを書く。後から画像を移動しても、当時の状態が分かる。

## 公開

- GitHub Pages に出すのは `artifacts/` のみ。
- CI は `artifacts/` から公開用ディレクトリを作り、そのディレクトリだけを Pages にアップロードする。
