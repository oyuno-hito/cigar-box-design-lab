# ワークフローと設計判断

これまでの検討で決めた方針の記録です。段階ごとの使い方は、`.cursor/skills/design-workflow/SKILL.md` にまとめています。

## 全体の流れ

```text
発散（生成）→ 評価（ふるい）→ 手直し → 仕上げ（simulator）→ 公開（artifacts/ → GitHub Pages）
```

| 段階 | 状態 |
| --- | --- |
| 発散 | 実装済み（`/eval-prompts`。ComfyUI で全件生成） |
| 評価 | 実装済み（人間の `好み` と `一致`。分類器は、同じ run 内の並べ替えに使い、足切りには使わない） |
| 手直し | 未実装（実使用のフローの後半として構想済み。img2img も未実装） |
| 仕上げ | 実装済み（別リポジトリの cigar-box-design-simulator） |
| 公開 | 実装済み（`tools/export_artifacts.py`、GitHub Pages） |

当初の想定は、ラベル付けから分類器を作って足切りし、VLM で再評価する流れだった。実際には、分類器は LLM 側の画像で学習していて SD 系の出力とは癖が違うため、全件を人間が見る運用になっている。分類器は、足切りではなく、並べ替えに使う（「分類器」の節）。

## 実使用のフローとモバイルからの運用

実験（`runs/`）とは流し方を分けた、実際に使うデザインを選ぶ流れ。出力先は `sessions/`（基本は Git 管理外。[sessions/README.md](../sessions/README.md)）。手順の正本は skill（`.cursor/skills/design-workflow/SKILL.md`）の「実使用のフロー」。

- **採点・レポート・人間の評価（好み / 一致）は作らない。** 分類器は、画像の生成直後に足切りするためだけに内部で使う。採用済みカードは後から削除しない。
- 流れは、前半（候補を絞る）と後半（1 枚ずつ微調整する）の 2 段。**前半は実装済み、後半は未実装。**
- 前半: 候補は 8 件。カードのページ（`tools/serve_session.py`）で見せる。AI がページの URL を返し、ユーザーがカードの枠をタップして選ぶ（選択は全カード共通）。カード内に、プレビュー（箱に貼った見た目。中に拡大表示）と、個別の方向のテキスト欄がある。下に全体の方針の欄が常にあり、ボタンは「選んだものを残して再生成」「選んだもので決定・微調整へ」。並び順は変えない。
- 通常の探索は、1 prompt につき画像 1 枚。同じ `idea_id` に複数の prompt があれば、最初にしきい値を超えた 1 枚を採用して、そのアイデアを終了する。予備が尽きても足りなければ、AI に新しいアイデアを依頼する。低スコアの画像はカードになる前に削除し、採用済みカードを後から削除しない。
- 再生成は、ボタンを押すとサーバーが `tools/session.py` を起動して行う（チャットで AI に頼まない）。選んだカードだけを残し（選んでいないカードは、個別の方向が入っていても捨てる）、予備のアイデアから新しい候補を埋める。選んだカードに個別の方向があれば、元の画像を残して、元の画像とはっきり違う派生を 3 件作る（img2img は使わない）。派生は元のカードの「派生」ボタンから見る。派生には全体の方針を反映しない。予備が尽きても自動では AI を呼ばず、人が「足りない分を補う」を押したときだけ頼む。カードの「説明」ボタンに、その案を採用した理由が出る。
- **AI は、最初のアイデア出し、「足りない分を補う」で頼む追加、個別の派生 prompt の作成に使う。** 元の prompt との距離（残りが 3〜8 割、方向の語句に重み付き、派生どうしが似すぎない）を機械的に調べ、外れたら差し戻す。カードの題名と、「説明」に出す採用理由は、AI が付ける。AI の呼び方はツールに依存しない: 環境変数 `CIGAR_COMPOSER_CMD`（依頼文を標準入力、返答を標準出力）で呼ぶか、未設定ならページで依頼文をコピーして任意の AI に貼り、返答の JSON をページに貼る。MCP は使わない（選択の受け渡しはページが担い、AI を自動で起こす仕組みは MCP にもないため）。
- 後半（構想）: 決定したカードを 1 枚ずつ、「そのまま残す」「画像を再生成（方向を入力、パターンを並べて複数選択、0 件も可）」「ツールで微調整（方向を入力、AI が動的に作る simulator、「選択して次へ」で終える）」から選ぶ。前半でカードに書いた個別の方向は、入力済みで開く。
- ページは認証なし。届く範囲は bind するアドレスで決める（既定 `127.0.0.1`、スマホからは `--host tailscale`）。公開リポジトリなので、誰でも GPU を使える状態にはしない。
- スマホから使うときの条件: PC でサーバー（`serve_session.py`）が動いていて、Tailnet から開けること。AI は、最初のアイデア出し、予備切れ、個別の派生 prompt の作成だけに要る（貼って渡す方式なら、どの AI アプリでもよい）。クライアントが外部のクラウドから接続する方式の場合は、Tailnet の中が見えないため、接続方式を決めるときに調べる。
- 先に決めること: `sessions/` と `runs/` の関係、`runs/` の画像を `generated/`（学習用の正本）へ昇格させる経路、`sessions/` の画像を `artifacts/` へ出す経路。

## 概念探索と最終生成

- 発散のための候補（概念探索）は、クラウドの画像生成を使ってもよい。
- ただし、クラウドの生成器で見つけた「方向性」と、最終的に使うモデルが「きれいに描けるか」は別問題。好きだった概念は、最終モデルで再生成して確認する。
- 分類器は生成元ごとに画像の癖が違うため、同じ生成元の画像どうしの順位付けにだけ使う。

## 探索と深掘りを分ける

- **探索（発散）:** 固定の rules と、組み合わせ表（配色 × 形 × 密度 × 対称性 × 線の太さなど）だけを渡す。好みの仕様書は渡さない。渡すと、既知の好みに寄って新しい発見が減る。
- **深掘り（収束）:** 仕様書と、好きな画像の例を渡して絞る。

仕様書（好みの仮説）は `docs/style-spec.md` に置く。必要になった時点で作る。更新は、ラベル付けの 1 ラウンドごとにまとめて行う。

## ディレクトリとラベル

- `generated/` が生成画像の正本。分類器用などに画像を複製しない。
- `like` / `dislike` / `maybe` の意味を固定する。詳細は [generated/README.md](../generated/README.md)。
  - `like`: 手直し・派生の方向が見えて、残したい。「そのまま使える完成品として好き」ではない。
    - `reference`: 既知のパターンとして残す（似た展開が想像できる）
    - `seed`: 未知の方向として残す（ここから複数の派生を見たい）
  - `dislike`: 興味がなく、発展させたい方向も思いつかない
  - `maybe`: 何かありそうだが、手直しの方向が見えない。分類器の学習には使わず、境界の把握や検証に使う
- 発散のラベルは、「具体的な変更案を 1 つ以上思いつき、その結果を見たいか」で決める。回転する道具としての上下・左右の方向性や印刷適性は、最終成形で評価し、発散のラベルには含めない。
- 点数づけ（100 点満点など）はしない。二値＋保留で、数ラウンド分類してから見直す。
- 画像ごとにメタデータ（プロンプト、生成元など）を残す。

## 分類の進め方

- 最初は第一印象で振り分ける。1 枚に長く悩まない。
- 一巡したら、`maybe` と、`like` / `dislike` のうち境界にあるものを見直す。
- 分類器ができたら、人間が見る順番は、自信のある `like`、予測が拮抗するもの、既存データに少ない色・様式のもの、の順にする。

## 分類器

- 分類器は並べ替え用であり、熱心には育てない。足切りには使わない。同じ run の中での順位は、人間の好みとよく合う（16 run・206 枚で、run 内 AUC の中央値 0.86。`design-workflow` の「分類器の位置付け」）。
- 判断の中心は VLM による再評価。ただし VLM の判定も、人間のラベルとの一致率で検証する。
- `scorers/` に、係数・マニフェスト・評価結果の JSON をコミットする。再学習したら上書きし、版の管理は Git の履歴に任せる。
- マニフェストには、参照した画像の ID・ハッシュ・その時点のラベル、埋め込みモデル、学習時点のコミットを書く。後から画像を移動しても、当時の状態が分かる。

## 公開

- GitHub Pages に出すのは `artifacts/` の画像と `site/` だけ。`.github/workflows/pages.yml` が `_site/` を作り、そのディレクトリだけをアップロードする。
