# プロンプト調整サイクル

既存の run で打率の低い題材を選び、プロンプトの「描き方」だけを変えて打率が上がるかを試す。
目的は、特定の様式を引き続けることではなく、**題材が変わっても通用する抽象的な性質**を `docs/style-spec.md` に残すこと。

## 守ること

- **探索（発散）には使わない。** このスキルは、題材が決まったあとの生成プロンプトの調整だけをする。アイデア出しや探索セットの作成に `docs/style-spec.md` を渡さない。
- **題材（concept）は変えない。** 変えるのは「描き方」の軸だけ。題材の言葉を足し引きして打率を上げるのは、調整ではなく題材の選び直し。
- **1 条件 = 1 つの変更**（1 軸 × 1 方向）。まとめて変えない。併用（`combo`）は、単独で効いたものだけを組み合わせる。
- **様式名で書かない。** 「浮世絵風」「ヴィンテージ風」ではなく、軸の語彙（`docs/style-spec.md` の「軸の語彙」）で書く。
- **打率だけで判断しない。** 類似度（条件内の画像が似ていく度合い）が悪化していないこと、別の題材でも効くことを確かめる。
- **人間のレビューが一次。** 機械の通過率と自己評価は暫定。
- コミットはしない。`runs/` の PNG と `report.html` は Git 管理外（テキストと `contact.webp` は管理対象。`runs/README.md`「Git での扱い」）。`generated/` には何も入れない（あれはラベル付け用）。

## 前提

- ComfyUI が起動している（`http://127.0.0.1:8188`。起動方法は問わない）。
- `uv sync` 済み（採点に使う。README の「開発環境」）。
- `scorers/` に分類器がある。

## 手順

### 0. 回数と範囲を決めて、宣言する

開始前に、次を決めてユーザーに伝える（質問はしない。変えたければ返信してもらう）。

- **対象**: 題材 1〜3 個。
- **最大ラウンド数**: 既定は 3。1 ラウンドの目安は、`(1 + 試す変更の数 K) × 12 枚`。K = 4 で 60 枚。
- **停止条件**（どれかを満たしたら止める）:
  1. 打率の改善が +15 ポイント未満のラウンドが 2 回続いた。
  2. 類似度が、`base` より 0.08 以上悪化した条件しか残らない。
  3. 最大ラウンド数に達した。
- 人間が見られないときは、自己評価（手順 5）で進める。その場合、結果は「暫定」と明記する。

### 1. 現状を見て、対象を選ぶ

```bash
uv run tools/summarize_runs.py
```

- 打率（人間 OK 率）が低く、**LLM 側の like 率は高かった**題材を優先する（ギャップが大きい = 調整の余地がある）。
- LLM 側の like 率が 0% の題材は、好みに合わない題材の可能性が高いので、優先しない。
- 「未確認」の条件は、人間のレビューを頼む。レビューがない条件は、打率の比較に使わない。

### 2. 診断する（OK と NG の違いを、軸で書く）

```bash
uv run tools/montage.py runs/<run-id> --condition <条件名>
```

`generator/temp/montage/` にできたシートを開いて見る。枠の色は、緑 = 機械が通過、赤 = 不通過、黄 = 人間が機械に同意しなかった画像。

- 人間 OK の画像と NG の画像を見比べて、**違いを軸で 2〜4 個**書く。各項目に、根拠の画像 id を付ける。
- 抽象化の確認: 「その性質は、題材を別のものに替えても意味が通るか」を毎回自問する。通らないなら、題材の話なので軸に書かない。
- 言い換えの確認: 同じ性質を、別の言い方でもう一度書いてみる。書けなければ、まだ具体的すぎる。

### 3. 変更案（knob）を作る

- 1 つの knob は、1 軸 × 1 方向を、**肯定形の短い句**で書く（例: 「面ごとの色数を 3 色以内にする」「主役を画面の端に寄せる」）。
- 避けたい性質は、反対側の性質を肯定する句にする（negative に頼らない。XL Turbo-Lightning は negative がほとんど効かない）。
- 1 ラウンドで試す knob は 3〜5 個。

### 4. run を作って流す

`runs/<日時>-tune-<題材>-r<N>/spec.json` を作る（形式は `runs/README.md`）。

- 条件は、`base`（現行のプロンプト）と、knob ごとの条件（`k1-…`）。2 ラウンド目以降は `combo` も。
- **項目（`items`）と seed は、全条件で同じ 12 件にする。** `base` は前のラウンドと同じプロンプトにして、再生成する（同じ環境でも結果は変わりうるため、比較は同じ run の中でする）。
- knob の句は `prompt_suffix` に入れる（`prompt_prefix` の題材部分は変えない）。

```bash
uv run tools/run_generate.py runs/<run-id>               # バックグラウンドで実行。条件順に出る
uv run tools/score_run.py runs/<run-id>
uv run tools/make_report.py runs/<run-id>
```

### 5. 評価する

評価が終わったら、`uv run tools/montage.py runs/<run-id> --contact` で `contact.webp`（Git 管理する一覧画像）を作る。

1. **人間のレビュー（一次）**: `uv run tools/make_report.py runs/<run-id> --serve` でレポートを開いてもらう（サーバーが動いていれば、一覧 `http://127.0.0.1:8765/` の未検査から開いてもらう）。条件ごとに「この条件を最後まで見た」をチェックし、「review.json に保存」を押してもらう（`report.html` と同じディレクトリに書かれる）。待つ間は、終わった題材から先に見てもらう。
2. **自己評価（人間が見られないとき）**: `montage.py` のシートを見て、画像ごとに「明確に OK / 明確に NG / 保留」を付ける。付けた結果は `self_review.json`（`{"ok": [...], "ng": [...]}` の画像 id）として run に保存し、`review.json` とは混ぜない。
   - 使う前に、**人間のレビュー済みの run で較正する**: 同じ題材の `base` を自己評価して、人間の判定と照らす。明確なものの一致が 80% 未満なら、自己評価は参考止まりにする。
3. **補助**: 機械の通過率（足切りは学習時の値が合わない題材がある。順位で見る）と、類似度。

```bash
uv run tools/summarize_runs.py runs/<run-id>
uv run tools/compare_review.py runs/<run-id>
```

### 6. 判定する

knob ごとに、次のどれかにする。

- **採用**: `base` より打率が上がり、類似度が大きく悪化していない。次ラウンドの `base` に取り込む。
- **保留**: 差が小さい、または枚数が少なくて判断できない。
- **却下**: 打率が下がった、または類似度が悪化した。

12 枚では、差が 2 枚以内なら偶然の可能性が高い。

### 7. 一般化を確かめる

採用した knob は、**別の題材**で、あり / なしを 12 枚ずつ比べる（1 枚ずつ幅広く試すなら `/eval-prompts`）。2 つ以上の別の題材で同じ方向に効けば「確認済み」。1 つの題材でしか効かなければ、「観察」か「仮説」のまま。

### 8. 記録する

`docs/style-spec.md` を更新する。

- 「好みの記録」の表: 軸、好む方向、避ける方向、**状態**（観察 / 仮説 / 確認済み / 却下）、根拠の run。
- 「打率の基準」の表と「モデルのメモ」、「履歴」。
- 軸に収まらない発見があれば、軸を足す。

### 9. 報告する（日本語で）

- 何ラウンド回したか、なぜ止めたか
- 打率と類似度の推移（表）
- 「確認済み」になった性質、「仮説」のまま残ったもの、「却下」したもの
- 評価が暫定（自己評価のみ）の部分
- 次にやるとよいこと（人間に頼みたいレビューなど）
