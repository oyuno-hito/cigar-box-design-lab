# 発散プロンプトの全件レポート

入力ブリーフ（曲名、または世界観・ムード）を 1 つ決め、**振れ幅が大きくなるように** 10〜20 本のプロンプトを作り、1 本につき 1 枚、**全件**を生成してレポートにする。足切りで絞らない。

目的は 2 つ:

1. **「あまりに気持ち悪い」画像が出ないプロンプトの書き方**を貯める（弾く境界を知る）。
2. **「こういうのが好きっぽい」の傾向**を貯める。ただし、発散なので、好みでないものが混ざるのは正常。

好みのものばかり出すことが目的ではない。`docs/style-spec.md` は、10〜20 本の**ガード**として使い、最後にまとめて更新する。

## 守ること

- **1 件の発散で、10〜20 本。** 既定は 15 本。同じ描画句を全員に足さない。方向・モチーフ・構図・色・密度・具象度・素材感をばらす。
- **全件出す。** 機械の通過・不通過で絞らない。分類器の値は参考（LLM 側の画像で学習している）。
- 1 本につき 1 つの主方向。複数を全部盛りにしない。
- 入力が曲のときは、周辺（MV、タイアップ作品、アーティスト、ジャンル、ダンス、制作の背景）から視覚の根拠を集める。歌詞は転載しない。人物・顔・衣装の再現はしない。
- 人物・手・建物・室内を主役にしない（写実に倒れる）。各プロンプトに `no text, no people, no hands` を入れる。
- プロンプトは英語。negative は使わない（XL Turbo-Lightning ではほとんど効かない）。避けたい性質は、反対側を肯定する句にする。
- seed は画像ごとに変える（発散のため）。
- コミットはしない。`generated/` には何も入れない。

## 前提

ComfyUI が起動している（`http://127.0.0.1:8188`）。`uv sync` 済み（README の「開発環境」）。`scorers/` に分類器がある。

## 手順

### 1. 入力ブリーフとコンセプトを決める

- 入力は `music`（曲名とアーティスト）か `mood`（世界観・ムード・雰囲気）。過去の run と重ならないものを選ぶ（`runs/` のディレクトリ名で確認する）。
- `concept`: 入力から、**核になるムード**を 1 文の英語にする。物体名の羅列にしない。強い形（輪、渦、放射など）を入れると、全員がそこへ収束する（`love-reason` の失敗）。形は入れない。
- 曲の場合は、知らない曲なら調べる。既知の曲で、時間をかけない場合は、調べていないことを `context_sources` の `source` に書く。

### 2. 10〜20 本を、大きく振って作る

土台は `flat graphic decoration, full frame composition` と、各プロンプトの `no text, no people, no hands`。その間に、1 本ごとに次を変える。

| 振る軸 | 振り幅の例 |
| --- | --- |
| 構図 | 中央 / 全面に分散 / 斜めの流れ / 帯 / 余白の多い片寄り |
| 密度・余白 | 疎で大きな余白 / 密 |
| 色 | 暗地 + 差し色 / 明るい地 / 単色 + 白 / 淡い 3 色 / 補色 |
| 素材感・描き方 | 切り紙の面 / 手描きの線 / 粒子のにじみ / 織りの目 / ベタ塗り |
| 具象度 | 題材の記号 / 半抽象 / 完全抽象 |
| 題材の切り口 | 曲なら MV、作品、ジャンル、ダンス、音の構造。ムードなら光、動き、温度、時間 |

- 01 は、入力の核を素直にまとめた基準案（`synthesis`）。
- 最後の 1〜2 本は `wildcard`: 入力を意外な抽象に解釈した案。
- `label` は `direction-…` / `synthesis` / `wildcard` など。`direction` に日本語で主方向を書く。
- 様式名は書かない。素材や面の性質で書く。

### 3. spec を作って流す

入力ブリーフの短い JSON（`generator/temp/briefs/<slug>.json`。形式は `tools/new_eval_run.py` の docstring）を書き、spec を作る。

```bash
uv run tools/new_eval_run.py generator/temp/briefs/<slug>.json    # runs/<日時>-eval-prompts-<slug>/spec.json を作る
uv run tools/run_generate.py runs/<run-id>                        # 生成（バックグラウンドで実行）
uv run tools/score_run.py runs/<run-id>
uv run tools/make_report.py runs/<run-id>
uv run tools/montage.py runs/<run-id> --sort id           # 作業用のシート（generator/temp/montage/）
uv run tools/montage.py runs/<run-id> --contact           # runs/<run-id>/contact.webp（Git 管理する一覧画像）
```

`runs/` は、テキスト（spec・scores・review・画像ごとの `.json`）と `contact.webp` だけを Git 管理する。PNG と `report.html` は管理外（`runs/README.md`「Git での扱い」）。

生成中に、次のブリーフを書く（ComfyUI は順番に処理する）。

### 4. 自己評価を書く

`montage.py` のシートを見て、`self_review.json` を書く（形式: `{"ok": [...], "ng": [...], "creepy": [...], "notes": {"p-01": "…"}}`）。

- `ok`: 好きそう。
- `ng`: 好みでなさそう。ただし、気持ち悪くはない（発散の範囲）。
- `creepy`: **あまりに気持ち悪い**。顔・人体の歪み、写実の質感、虫や生き物の集合、崩れた文字、色のチカチカなど。理由を軸の語彙で `notes` に書く。
- 保留は、どれにも入れない。

発散の人間評価では、**好みとコンセプト一致度を混ぜない**。少なくとも次の
2 軸を別々に記録する。

- 好み: その画像をシガーボックスのデザイン候補として残したいか。
- コンセプト一致: 共通の核と、その画像に割り当てた方向が見えるか。
- 気持ち悪さ: 上の `creepy` として別に記録する。

判定の読み方は、好み高・一致高が採用候補、好み高・一致低が面白いが
お題から外れた発見、好み低・一致高が核は正しいが自分の好みではない案、
好み低・一致低が失敗である。発散では「好み高・一致低」も捨てず、
`style-spec` の好みと、コンセプトを保つためのプロンプト改善を分けて考える。
一致度は、全画像に同じ表現を要求するのではなく、共通の核と各画像の
`direction` の両方で見る。

人間のレビューは、離席中などで後から行う。レポートは一覧の「未検査」に出る。レビューが終わったら `uv run tools/montage.py runs/<run-id> --contact` で `contact.webp` を作り直す（印が枠に入る）。

### 5. 最後にまとめて `docs/style-spec.md` を更新する

複数件を回したあと、まとめて更新する。

- 「好みの記録」: 気持ち悪さの原因（写実の質感など）と、好みの傾向を、軸の語彙で追記する。根拠に run と画像 id を書く。
- 「試す句の案」: 気持ち悪さを抑える句、好みに寄せる句を足す。
- 「履歴」に 1 行ずつ。
- 人間のレビューがない結果は「観察」止まり。「確認済み」にしない。

### 6. 報告する（日本語で）

- 回した件数と、各件の入力・主な振れ幅・気持ち悪い画像の数。
- 気持ち悪さの原因の傾向（軸ごと）。
- 好みの傾向。
- 評価が暫定（自己評価のみ）の部分。
