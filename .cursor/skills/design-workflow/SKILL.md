# デザインワークフロー（全体案内）

シガーボックスジャグリングの道具（180x120mm / 165x120mm の面）に貼るデザインを、AI で発散的に探して、採用したものを公開するまでの流れ。このファイルは**案内役**。各段階の細かい手順は、リンク先の skill と文書に書いてある。

流し方は 2 種類ある。

- **実験（`runs/`）**: 描き方の傾向を調べて、好みを記録する。採点・レポート・人間の評価（好み / 一致）を付ける。実装済み。以降の「段階」はこちら。
- **実使用（`sessions/`）**: 実際に使うデザインを、AI と対話しながら選んで仕上げる。採点やレポートは作らず、結果はカードのページで選ぶ。前半（候補を出す・選ぶ・個別の方向・残して再生成・プレビュー）は実装済み。後半（1 枚ずつの微調整）は未実装。「実使用のフロー」を見る。**お題を受けたときの既定はこちら。**

## 段階と現状

| 段階 | やること | 状態 | 使うもの | 実行する場所 |
| --- | --- | --- | --- | --- |
| 1. 発散 | お題（曲・ムード）から 10〜20 方向を全件生成する | 実装済み | `/eval-prompts` | ComfyUI のある PC |
| 2. 評価 | 一覧を見て、好み（残す / 保留 / 外す）と一致（強い / 部分 / 弱い）を付ける | 実装済み | `make_report.py` / `serve_runs.py`、`runs/README.md` | 目視だけなら端末は問わない |
| 3. 手直し | 選んだ画像を、指示で直す | **未実装**（実使用のフローの後半として構想済み。画像を入力にする微調整（img2img）も未実装） | 「実使用のフロー」、下の「手直し」 | ComfyUI のある PC |
| 4. 仕上げ | 箱に貼った仕上がりを確認し、色・サイドテープを決める | 実装済み（別リポジトリ） | [cigar-box-design-simulator](https://oyuno-hito.github.io/cigar-box-design-simulator/draft/) | ブラウザ |
| 5. 公開 | 採用した画像を `artifacts/` に置き、GitHub Pages に出す | 実装済み | `tools/export_artifacts.py`、`site/README.md` | PC |
| （補助）調整 | 描き方の軸を調整し、`docs/style-spec.md` に抽象的な性質を残す | 実装済み | `/tune-prompts` | PC |
| （補助）学習 | ラベル付けした画像から分類器を作る | 実装済み。**足切りには使わず、並べ替えに使う** | `tools/train_scorer.py`、`scorers/README.md` | PC |

## 全体で守ること

- 返答とドキュメントは日本語。
- **探索（発散）に `docs/style-spec.md` を渡さない。** 渡すと既知の好みに寄る。使うのは、題材が決まったあとの調整（`/tune-prompts`）だけ。
- 画像は 3:2。出力した画像には、同名の `.json`（プロンプトと生成元）を残す。
- `runs/` にコミットするのは、テキストと `contact.webp` だけ。PNG と `report.html` はコミットしない（`runs/README.md`「Git での扱い」）。
- API キーや認証情報を書かない・コミットしない。
- コミットは、頼まれたときだけ行う。
- 外部から画像を生成する仕組みを足すときは、接続できる範囲を自分の環境に限る（公開リポジトリなので、誰でも GPU を使える状態にしない）。

## お題を受けたとき（最初にやること）

曲名・ムード・参考画像などのお題が来たら、**案を並べて止まらず、候補を生成して、カードのページの URL を返すところまで進める**。「考えたい」「デコレーションを作りたい」のような頼み方でも同じ。案だけを求められたと明言されたときだけ、生成しない。実験（`runs/`、評価の記録を残したいとき）と頼まれたときは、`/eval-prompts` に従う。

1. 参考画像（衣装など）は、色・形・質感の根拠として `context_sources` に書く。人物・衣装そのものは再現しない。
2. ComfyUI の応答を確かめる: `curl -s http://127.0.0.1:8188/system_stats`
3. 応答がなければ、起動する。`generator/start_comfy.sh > /tmp/cigar-comfy.log 2>&1` をバックグラウンドで実行し、応答するまで待つ。**「画像を生成するツールがない」と判断して止まらない。** 生成は、Shell から ComfyUI の API を呼ぶ `tools/session.py` で行う（`GenerateImage` などのツールは使わない）。
4. 止まってよいのは、ComfyUI を起動できないとき（モデルが置かれていない、ポートが使われているなど）だけ。その場合は、理由と直し方を示す。
5. 「実使用のフロー」の「1. 候補を出す」へ進む。

## 1. 発散

`/eval-prompts` に従う。お題を決め、方向を大きく振った 10〜20 本を全件生成して、`runs/<日時>-eval-prompts-<slug>/` に残す。

- 前提: ComfyUI が起動している（`generator/start_comfy.sh`）。生成を流している間に、次のお題を考える。
- 流れをまとめて動かすのは `sh tools/eval_pipeline.sh runs/<run-id>`（生成 → 採点 → レポート → 一覧画像）。

## 2. 評価

発散の評価は、**目視の好みが一次**。機械の通過・不通過で絞らない。

- 見る: `contact.webp`（`uv run tools/montage.py runs/<run-id> --contact`）または `report.html`。
- 付ける: `好み`（残す / 保留 / 外す）と `一致`（強い / 部分 / 弱い）。結果は `review.json` の `ratings`。
- 人が見られないときは、自己評価を `self_review.json` に書く（`review.json` と混ぜない。形式は `/eval-prompts`）。
- 評価が終わったら、`contact.webp` を作り直す（印が枠に入る）。
- 採用候補になった画像は、段階 5 で `artifacts/` に出す。ラベルの意味（`like` / `dislike` / `maybe`）は `generated/README.md`。

### 分類器の位置付け

- 分類器（`scorers/`）は LLM 側の画像 312 枚で学習している。SD 系の出力とは画像の癖が違うので、**通過・不通過の足切りには使わない**。
- **同じ run の中での並べ替えには使える。** `review.json` に好み（残す / 外す）を付けた 16 run・206 枚で確かめた。run 内の順位の AUC は中央値 0.86（全 run を混ぜると 0.73）。スコアの下位 3 分の 1 を落とすと、落とした中の「残す」は 13%、残した中は 57%（全体は 42%）。落として失う「残す」は全体の 10%。
- この確認は、同一人物の好みによる評価で、1 run が 12〜24 枚。傾向として扱う。
- 生成数が増えて全件を目で見られなくなったら、`review.json` にたまった SD 系の評価で作り直す。
- `runs/` の画像を `generated/` へ移す経路は、まだ決めていない。決めるまでは、`runs/` の画像から `generated/` へ入れない。

## 3. 手直し

手直しは、実使用のフローの後半として構想している（未実装）。画像と指示で直す方法も、まだ入っていない。構想は 2 系統ある。

1. **画像から再生成（img2img）**
   - 元画像を入力にして、指示を反映したプロンプトで、denoise を 0.4〜0.7 に抑えて作り直す。いまのモデル（SD 系）のままできる。
   - 必要なもの: ComfyUI に画像入力のワークフロー（`LoadImage` と `VAEEncode` を足したもの）、`tools/` に手直しの run を作るツール。
   - 「ここだけ直す」ような指示どおりの編集まで求める場合は、編集用のモデルが別に要る。選定してから決める。
2. **simulator で微調整**
   - 色・余白・サイドテープは、simulator の `/preview/` で決められる。画像の形そのものを動かしたいときは、`/draft/` で AI が調整ページを作る（人が間に入る）。
   - 画像の URL を渡して `/preview/` を開く入口は、simulator 側にまだない。

画像を入力にする手直しを頼まれたときは、未実装であることを先に伝え、どちらの系統で進めるかを確認してから作る。プロンプトの書き換えで足りるときは、「実使用のフロー」の前半の再生成で進める。

## 実使用のフロー

実際に使うデザインを、AI と対話しながら選んで仕上げる流れ。実験の `runs/` とは目的が違うので、記録の置き場も流し方も分ける。コマンドの詳細は `sessions/README.md`。

全体は **前半（候補を絞る）** と **後半（1 枚ずつ微調整する）** の 2 段。満足するまで前半を繰り返し、決めたものだけを後半へ進める。

- **前半: 実装済み。** アイデア単位の候補生成、生成直後の足切り、共通の選択、残して再生成、プレビュー、「決定・微調整へ」の選択の受け渡しまで。
- **後半: 未実装。** 構想は「後半（微調整）」に書いた。頼まれたら、未実装であることを先に伝える。

### 決めていること

- **採点・レポート・人間の評価（好み / 一致）・`contact.webp` は作らない。** 分類器は、生成直後の足切りにだけ内部で使い、スコアは見せない（`state.json` の内部値。ページの API にも出ない）。採用済みカードを後から削除しない。
- 出力先は `sessions/<日時>-<名前>/`。**基本は Git 管理外。** 例示として 1 件だけ入れるときは、`spec.json` と `state.json` を `git add -f` する（画像は入れない）。
- 候補は **8 件**（`session.py new --size`、既定 8）。分類器のしきい値未満の画像はカードになる前に削除して、ページに出さない。
- 選択は、カードの枠のタップで行う。**選択はページ全体で 1 つ**（共通）。「残す」「手直し」のような区別はない。カードごとに書けるのは、「この画像をこの方向に」という個別の方向だけ。
- 候補は、カードのページ（`tools/serve_session.py`）で見せる。**AI はページの URL を返し、ユーザーがページで選ぶ。** 画像のデータも選択の結果も、チャットのクライアントを通らない。ボタンを押したら、ユーザーが「選んだ」と伝え、AI が `session.py selection` で読む。
  - 応答の本文に HTML や画像のデータを埋め込まない（AI がデータを出力する必要があり、壊れやすい）。
  - ページを開く範囲は、bind するアドレスで決まる（認証がない）。既定は `127.0.0.1`（この PC だけ）。スマホから開くときは `--host tailscale`（Tailnet の端末だけ）。`0.0.0.0` は使わない。

### 前半の操作

ページの操作は次のとおり。

- **選ぶ**: カードの枠をタップする（選んだ枠は緑になる）。
- **プレビュー**: カード内のボタン。箱に貼った見た目で確かめる（一箱 / 縦 / 横、側面の色、枠線）。プレビューの中の「拡大表示」で、画像を細かく見られる。
- **説明**: カード内のボタン（プレビューの隣）。その案を採用した理由が出る。最初の候補は brief の `reason`、AI が書く案は AI の返答の `reason`、理由がない派生は元の方針と方向から作る文。
- **個別の方向**: カード内のテキスト欄。書くと、そのカードを自動で選ぶ（あとで選択を外せる）。**選んだカードの方向だけが有効**で、選んでいないカードは、方向が入っていても捨てられる。選んだカードは元の画像を残したまま、**派生を足す**（「派生作成」のラベルが付く）。派生には「派生」のラベルが付く。
- **派生**: 元のカードの「派生 n」ボタンから見る（グリッドには出さない。件数にも数えない）。選んだ派生だけ、次の再生成で残る。元のカードを選ばずに派生だけ選ぶと、派生が元のカードの代わりになる。
- **全体の方針**: 下に常に出ている欄（任意）。新しい候補すべてに反映する。
- **並び順**: 変えない。残したカードは前の順、新しいカードは、できた順。分類器は、下位を捨てる判定にだけ使う（並べ替えには使わない）。
- 下のボタン:

| ボタン | 意味 |
| --- | --- |
| 選んだものを残して再生成 | 選んだカードだけを残し、それ以外は削除して、予備のアイデアで 8 件まで埋める。予備が尽きても AI は呼ばず、足りない件数を出す |
| 足りない分を補う | 8 件に届かないときだけ出る。人が押したときだけ、予備を使い、尽きたら AI に新しいアイデアを頼んで補う |
| 選んだもので決定・微調整へ | 選んだカードで前半を終える（1 枚以上が必要）。後半へ進む |

**ボタンを押すと、サーバーが処理を始める**（チャットで AI に頼む必要はない）。

- **通常の探索**: 1 プロンプトにつき 1 枚を生成する。同じ `idea_id` に複数の prompt があれば、最初にしきい値を超えた 1 枚を採用し、そのアイデアの残りは生成しない。
- **予備が尽きるまで**: まだ試していないアイデアを順番に使う。8 件に届かなくても、再生成は AI に新しいアイデアを頼まない（人の指示を待つ）。「足りない分を補う」を押したときだけ頼む。
- **個別の方向**: 派生 prompt を 3 件作り、各 prompt から 1 枚ずつ生成する。元の画像を残し、派生は分類器の足切りをせずユーザーに見せる。seed 違いを発散の手段にはしない。派生は、元の画像と**はっきり違う**ことを求める。
- **全体の方針**: 予備から作る新しい候補に反映する。
  - **個別の方向を書いたカードの派生には、全体の方針を反映しない**（個別の方向だけ）。全体の方針は、空き枠を埋める新しい候補にだけ反映する。この規則は、AI への依頼文（`session.py plan` の `instruction`）に入っている。
  - **派生の書き方**: 方向の語句を前のほうに置いて `(語句:1.3)` の重みを付け、方向と矛盾する元の語句は取り除く。3 件は、方向の解釈を変える（形・配置・密度・色数）。機械的な検査: 元の語句の残りが 3〜8 割 / 派生どうしの共通が 8 割以下 / 重み付きの語句がある。満たさなければ、理由を添えて 1 回だけ頼み直す（0 割は別の絵になるので差し戻す。8 割超は変化が弱い）。風景を連想させる語（space, field, network など）は、風景に化けやすいので形の語で書く（実際に、network と quiet empty space で風景画が出た）。
  - **補充（全体の方針の反映）**: 元の語句は 3 割以上残す。
  - **タイトルと理由**: AI が、元の方針と方向を合体させた短い日本語の方針（カードの題名）と、採用した理由（「説明」ボタンに出る）を返す。方向の文言や「別の seed」は、題名に入れない。

AI の呼び方は、ツールに固定しない。

- 環境変数 `CIGAR_COMPOSER_CMD` に、依頼文を標準入力から読み、返答を標準出力へ出すコマンドを入れて、`serve_session.py` を起動すると、サーバーが呼ぶ。例: `CIGAR_COMPOSER_CMD='claude -p'`。依頼と返答は `sessions/<id>/compose_logs/` に残る。ファイルの編集やコマンドの実行をさせない設定で呼ぶこと（ページの入力が依頼文に入るため）。
- 未設定のときは、ページに依頼文が出る。コピーして任意の AI に貼り、返ってきた JSON をページに貼る。
- チャットの AI が直接やるときは、`session.py selection` で選択を読み、`session.py plan` の `instruction` に従ってプロンプトを書き、`regen --items`（項目を直接書く）で再生成する。

**1. 候補を出す**

1. お題から、方向を大きく振った**アイデア**を、`size` 件より**多め**（目安は 3 倍）に書く。同じ `idea_id` に、描き方の異なる prompt を複数書いてよい。1 prompt につき画像は 1 枚。brief の JSON は `tools/new_eval_run.py` と同じ形式（`generator/temp/briefs/<slug>.json`）。各アイデアに、**採用した理由 `reason`（日本語 1〜2 文）**を書く（カードの「説明」に出る）。`brief`（題材の文）は、ユーザーの依頼の言葉をそのまま使い、禁止事項（「〜にはしない」）を自分で足さない。歌詞に含まれる特徴的な語（説明ではなく、語の抜粋）は、モチーフとして使ってよい。JSON は手で書くと崩れやすいので、`session.py new` は末尾のカンマ・コメント・コードフェンス・閉じ忘れ・要素間のカンマ抜けを自動で直して読む（直した内容は stderr に出る）。直せないときは、行と周辺を示して止まる。
2. 作って、生成する（生成はバックグラウンドで実行する）。

```bash
uv run tools/session.py new generator/temp/briefs/<slug>.json   # sessions/<id>/ を作る（既定 8 件）
uv run tools/session.py generate sessions/<id> > /tmp/session-gen.log 2>&1   # 生成 → 直後に足切り → 8 件に達したら終了
uv run tools/serve_session.py --host tailscale > /tmp/session-serve.log 2>&1   # 配信。起動済みなら不要
```

3. ページの URL を、生成を始めたらすぐ返す（`serve_session.py` の起動時の表示の `最新:`）。しきい値を通った画像だけが、できた順にカードへ出る。8 件に達したら終了し、カードを後から絞り直さない。

**2. 決定して微調整へ**

「選んだもので決定・微調整へ」を押すと、`selection` の `action` が `finalize` になり、`keep` の画像が決定。後半へ進む（未実装なので、いまは決定した画像の一覧をユーザーに返して、段階 4・5 へ進むか確認する）。

### 後半（微調整）— 構想・未実装

決定した画像を 1 枚ずつ精査する。**1 枚ずつ見るので、候補を複数並べない**（再生成だけは、パターンを並べて選ぶ）。選んだカードに対して、順に次のどれかを選ぶ。

| 選択 | 内容 |
| --- | --- |
| そのまま残す | 何もせず、次へ |
| 画像を再生成 | 方向をフリーテキストで入力する（前半でカードに書いた個別の方向が入力済み）。いくつかのパターンを生成して並べ、採用するものを選ぶ（複数可、0 件も可） |
| ツールで微調整 | 方向をフリーテキストで入力する（前半でカードに書いた個別の方向が入力済み。ほかは既存の仕様のまま）。AI が、その方向に合わせて動的に作る simulator を表示する。保存ではなく「選択して次へ」で終える |

- 同時に生成できる画像は 1 枚なので、ユーザーの選択（そのまま / 再生成 / ツール、方向）は先にまとめて受け取り、AI がプロンプトを一度に書いて、生成をキューに積む。できたものから順にユーザーへ見せる。
- ツールで微調整は、まず simulator の preview 相当（色・余白・サイドテープ）から作る。画像の形そのものを動かすときは、AI が作る調整ページ（`/draft/`）にする。

### 注意

- ページのボタンで始まる処理は、サーバーが `tools/session.py` を起動して行う。AI は、ユーザーがボタンを押す前に `regen` / `add` を実行しない。
- `generate` / `regen` / `add` は、完了を待つので、バックグラウンドで実行する。失敗すると `phase: error` になり、理由が `status` とページに出る。
- ComfyUI が止まっていたら、お題を受けたときの手順の 3 で起動する。
- ページには認証がない。サーバーが処理を起動するので、届く範囲（`127.0.0.1` か `--host tailscale`）を広げない。

## 4. 仕上げ

simulator（別リポジトリ）で、箱に貼った仕上がりを確認する。SVG は 1 単位 = 1mm、箱の面と同じ大きさにする。手順は simulator の README を見る。

## 5. 公開

```bash
uv run tools/export_artifacts.py runs/<run> --id <テーマID> --title '<テーマ名>' --kind song --pick 01,03,07
uv run tools/build_site.py --serve        # 確認（http://127.0.0.1:8000/）
```

- 公開するのは `artifacts/` の画像と `site/` だけ。プロンプト・スコア・好みの評価は載せない。
- 箱の色や枠線は、`artifacts/manifest.json` の `box` で決める（`site/README.md`）。
- `main` に push すると、GitHub Pages が更新される。

## スマホなど別の環境から進めるとき

構想は `docs/workflow.md`「モバイルからの運用（構想）」に書いてある。実装はまだない。

- 生成・選択・再生成は、PC のサーバー（`tools/serve_session.py`）のページで進める。スマホからは Tailnet 経由でページを開く。MCP は使わない方針（選択の受け渡しはページが担う）。AI は、最初のプロンプトを書くときと、メモの合成のときだけ要る。後者は、`CIGAR_COMPOSER_CMD` か、依頼文をコピーして任意の AI に貼る方式で、ツールに依存しない。
- いま環境が違っても進められるのは、次のものだけ。
  - リポジトリを読んで、お題の `spec.json` を作る（生成は PC で行う）。
  - `contact.webp` と `review.json` を見て、評価を相談する。
- PNG は Git に入っていない。別の環境で画像が要るときは、`runs/README.md` のとおり再生成する（同じ画像になるのは、同じ Mac だけ）。
